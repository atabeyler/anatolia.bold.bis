# Internationalization

The application is i18n-first from its very first implementation, and in
every subsequent change — no user-facing string is ever hardcoded.

## Supported languages (6)

| Code | Language | Direction |
|---|---|---|
| `en` | English (default/fallback) | LTR |
| `tr` | Turkish | LTR |
| `de` | German | LTR |
| `fr` | French | LTR |
| `ar` | Arabic | RTL |
| `ru` | Russian | LTR |

## Structure

```
client/src/i18n/
  config.ts               # i18next setup, document lang/dir sync
  locales/
    en/translation.json
    tr/translation.json
    de/translation.json
    fr/translation.json
    ar/translation.json
    ru/translation.json
```

Every locale file must carry exactly the same set of translation keys as
`en/translation.json`. `client/src/i18n/locales.test.ts` enforces this in
CI — it fails if any locale's key tree diverges from English's.

## Document language and direction

`config.ts` sets `document.documentElement.lang` and
`document.documentElement.dir` on init and on every language change.
Arabic renders `dir="rtl"`; every other supported language renders
`dir="ltr"`.

## Locale-aware formatting

Dates, numbers, percentages, and timestamps should use locale-aware
formatting (e.g. `Intl.DateTimeFormat`/`Intl.NumberFormat` keyed off the
active i18next language) rather than a fixed format — not yet needed in
Phase 1 since no such data is rendered yet, but required from the first
feature that renders any.

## Backend error localization

The backend never returns human-readable error text. It returns a stable
`code` and a `messageKey` (see `API.md`); the frontend resolves
`messageKey` against the active locale.
